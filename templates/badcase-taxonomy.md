# BadCase 归因分类表

归因的目的不是统计错误数量，是定位「下一步该改什么」。同一类错误反复出现，说明设计有系统性问题，不是调提示词能解决的。

## 记录格式

```markdown
### Case [编号]
- 输入摘要：
- 期望输出：
- 实际输出：
- 归因类别：（见下表）
- 根因判断：
- 改动内容：
- 回归结果：（通过 / 仍失败 / 引入新问题）
```

## 归因类别

| 类别 | 表现 | 通常该改哪里 |
|---|---|---|
| 输入理解 | 切错意图、漏掉明示约束 | 输入结构 / 意图识别规则 |
| 边界失效 | 该拒的没拒、该转人工的没转 | 能力边界定义与触发条件 |
| 输出质量 | 格式错乱、冗余、自相矛盾 | 输出契约 / 校验脚本 |
| 上下文丢失 | 前文约束未保持、重复造轮子 | 分块策略 / 断言自检机制 |
| 工具调用 | 选错工具、参数错、失败未兜底 | 工具描述 / 异常回滚设计 |
| 评测集本身 | 预期定义有歧义、评分口径不一致 | 先修评测集，别改 Agent |

**第六类最容易被忽略。** 如果一类 case 连人都判不清「什么算对」，不要急着改系统——先修评测集。

## 保留原则

- 变差的 case 必须保留，不能因为「这轮分数涨了」就删掉
- 边界外 case 单独统计，不混进主分数
- 每条 case 的改动只对应一个变量，便于回溯
